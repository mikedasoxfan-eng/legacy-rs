# Release 1.0 blocks area, round 2

This round closes live item/block connections and source mismatches from the merged round-1 implementation. It does not satisfy the task's Done criterion: `tools/oracle10`, `tools/verify10.sh` and the Release 1.0 bytecode harness are absent from this worktree. No oracle10 or verify10 infrastructure was created. All 136 blocks classes and the 10 explicitly owned container/recipe classes below remain **Not done** until a complete delta is verified against original bytecode; rows distinguish missing implementation from missing verification. Existing implementation descriptions are inherited from round 1 unless the row identifies a round-2 correction.

Sources: original 1.0 MCP Java at `C:/Users/logiu/Desktop/Projects/minecraft/beta-rs/tools/retromcp-r10/minecraft/src/net/minecraft/src`, compared with linked Beta 1.8.1 source and `tools/r10/renames.json`. Tracked changes are confined to `crates/worldgen10` and this report; validation artifacts and the requested commit script are under ignored `target/`. Protected Beta crates/oracles/verification scripts and all client crates are unchanged. Nothing was committed.

## Changes and boundaries

- Connected splash potion and pearl use, dispenser splash heading, ordinary pumpkin snowman creation and End portal collision. Corrected portal factory ordering and brewing-stand removal counts visible through retained tile objects.
- Connected enchantment consumers in combat, damage, breathing, digging, armor/tool/bow/fishing/flint/hoe wear and loot. Modifier random is process-wide and independent of World/item/entity random. Unbreaking checks the player's held item and skips an entire positive damage call; break animation precedes break stat, stack decrement and damage reset. Player damage retains the source's two virtual armor/protection passes.
- Added retained mutable compound handles and mutable potion-list handles; fixed first-match versus malformed-tag exception order. Shared potion cache supplies brewing, drinking and splash effects. Copy/split still deep-copy compounds, and drinking copies effects.
- Fixed enchanting slot recompute count and shift-transfer behavior; supplied configurable ItemColored name-array/captured-block callbacks, signed damage forwarding and callback-before-suffix-read order.
- Connected packed neighbor light to 1.0 Block flags; added height10 input to ItemBlock/mushroom/vine/door/piston boundaries; provider ID to ItemMap; eternal End bedrock fire; notify=true to sapling-generated trees. Corrected mushroom spread probability and its invoked giant-mushroom soil/placement checks.

Cross-area edits are limited to the consumer boundaries in `entity/living.rs`, `entity/living10.rs`, `entity/player.rs`, `entity/player/{controller,interactions,mechanics,placement,items}.rs`, `entity/{physics,fishing,item_stack,potion}.rs`, `features.rs`, `maps.rs`, and World height/light/cache/tick dispatch. Changes do not extend to unrelated entity behavior, the full terrain/provider system or renderers. The duplicate private PotionHelper parser/effect supplier in `entity/potion.rs` was removed when its public supplier was delegated to the block-owned shared cache. Giant-mushroom soil/height changes in `world/plants181.rs` are the smallest generator bridge needed by BlockMushroom. `tests/nether_dimension.rs` now checks that WorldChunkManagerHell fills only the requested prefix of a reused temperature array, preserving its tail; Java source confirms the prior test expectation was wrong and production biome code was not changed.

Remaining implementation dependencies:

- **ItemEnderEye:** right-click callback logic exists, but ordinary right-click has no exact World Stronghold locator. Existing generator lookup does not supply the 1.0 portal-room center/start traversal/fallback behavior. EntityEnderEye and target APIs exist; the final item connection requires that world API.
- **Biome colors/client:** BlockGrass/Leaves/Vine/TallGrass/Fluid source callback helpers exist, but ordinary client tint paths still use Beta climate logic. Biome-owned 1.0 RGB providers and client delegation, particles, GUI and renderer consumers remain outside this port.
- **Mutable registry/object identity:** generic ItemRegistry setters and ItemColored helpers are separate from fixed live registry/subclass dispatch. Captured Block identity across registration replacement, custom potion ingredient mutations, and dynamic enchantment/PotionHelper registration/maps need a shared mutable registry model. Default registrations continue to work.
- **NBT/cache identity:** top-level shared compounds/lists now retain mutations, but nested NBT tags and individual PotionEffect objects are values; full object graph aliases, Java iterator fail-fast behavior, public nested reference APIs and detached ItemStack count/damage aliases remain unrepresented. Sidecar entries persist for process lifetime. Rust panics label source exception classes but are not Java exception objects.
- **Entity/world context:** no-World remote health adjustment retains its legacy armor wear path; looting resolves live attackers in World, so detached/negative player-placeholder object identity requires entity-owner work. height10 supplies block/item boundary input, while chunks/generators/light storage are still fundamentally 128 tall. Full End provider/terrain and MapData changes are world-owned.

## Proposed exact checks

When the harness arrives, implement each row as Java `Mode_R10Blocks2_<Class>` and a corresponding Rust comparison mode `r10blocks2.<Class>`. Run them from `tools/verify_r10blocks2.sh`, with one `== r10blocks2.<Class>` section, `mkdir -p` outputs, no `set -e`, and append that suite before verify10 final pflush. These are proposed names only; no modes/suites currently exist. Execute original bytecode rather than recompiling the MCP algorithm. For each check compare serialized return values, integer values/raw float and double bits, exception class, null/object identities, every RNG state (including static RNGs seeded through harness reflection), NBT and ordered callback/read/write/event traces. Test server/remote/creative variants where applicable.
