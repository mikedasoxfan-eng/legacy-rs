# Beta 1.8.1 release play QA

Tested on Windows on 2026-10-05 with the real `target/release/beta.exe --mc b1.8.1`, built using `cargo build --release -p client`. The release build passed before testing and after the local script-hang fix. No game crash, panic, or save corruption was observed. One automation hang was reproduced and fixed. Two visible game UI issues and one script input limitation remain open, detailed below.

All six requested coverage areas were exercised. The final falling sword attack is confirmed by critical particles, one sword use, 16 damage, a mob kill, and an XP orb. Earlier screenshots with optimistic names such as `nether_arrival` or `critical_kill` are explicitly rejected where the action did not actually happen.

## Method and artifacts

Input used the repository's `--play-script` driver. Every launch used a separate options directory under `target/qa/`; screenshots, logs, helpers, and saves are also there. The Minecraft application-data directory was not modified. No commits were made. Screenshots were opened as PNGs and judged visually; the complete reviewed-image list is [screenshot-review.json](../target/qa/screenshot-review.json).

Menu tests created real worlds through the GUI. For repeatable item, damage, bed, and portal tests, [nbt_qa.py](../target/qa/nbt_qa.py) prepared copies of a real seed-1 save: a flat test area, specified inventory/health/time, and controlled mobs or structures. These fixtures are QA saved data, not changes to the simulator. Crafting, eating, combat, block placement, flight, sleeping, lighting a portal, and travel were then performed by game input. Native mouse-wheel dispatch was not independently exercised; the script wheel limitation is recorded as Q4.

Script names below are files in `target/qa/`. All paths in the evidence column are relative to that directory. The screenshots are 854 by 480 pixels. Complete per-run logs use the script stem plus `.log`; some runners also recorded arguments, exit codes, and durations in `run-results-*.json`, `portal-v3-run.json`, and `enter-critical-runs.json`. PowerShell's `NativeCommandError` wrappers in some logs describe ordinary stderr world-load messages, not a game panic. All completed game runs exited 0. The original `creative.txt` process was stopped after its script stalled at Title (Q1).

## Problems and code causes

### Q1 — Fixed: direct-start script stops forever after Save and Quit

Reproducer: original `creative.txt` launched with `--world-dir target/qa/creative-fixture`. At tick 675 it clicked Save and Quit. The world saved and Title appeared, but the requested Title shot at 725 and quit at 745 never ran. The process remained alive until explicitly stopped. Last successful screenshot: [creative/blocks_overview.png](../target/qa/creative/blocks_overview.png). This was a script-driver hang, not a save corruption or frozen Title UI.

Cause: [crates/client181/src/app.rs](../crates/client181/src/app.rs), `App::script_step` and the script clock in `App::frame`. Both allowed menu scripting only when immutable startup option `opts.direct` was false. Closing a directly loaded world makes `ready` false while `opts.direct` stays true, so both command execution and tick advancement stop.

Local change: recognize the actual unloaded menu state with `!self.ready && self.loading.is_none()` in both places. Loading still waits for the world/player. This is the only production source change; no simulation behavior changed. Release rebuild passed. `hang-regression.txt` then reached [after_quit_world.png](../target/qa/hang-regression/after_quit_world.png) and exited normally. Subsequent world-list/reload and direct-start runs also completed.

### Q2 — Open: death screen prints a formatting token

Observed literal `Score: &e0` on [combat/sword_falling.png](../target/qa/combat/sword_falling.png). Cause: [crates/client181/src/gui/screens/game_over.rs](../crates/client181/src/gui/screens/game_over.rs), `GuiGameOver::draw_screen`, formats `Score: &e{}`. The font's formatting escape is the section sign, so the ampersand token renders literally. This is a visible text-formatting defect; left unchanged under the task's fix restriction.

### Q3 — Open: sleeping view has no Leave Bed screen/button

[bed-v2/sleeping.png](../target/qa/bed-v2/sleeping.png) shows the sleeping viewport without a Leave Bed control. Sleep itself works: the same run wakes at morning. Cause: [crates/client181/src/app.rs](../crates/client181/src/app.rs), `App::frame` handling `FromWorker::Player`, copies `hud.sleep_timer` to the HUD but does not transition to a sleeping GUI. [gui/screens/mod.rs](../crates/client181/src/gui/screens/mod.rs) has no sleeping screen, and [minecraft_input.rs](../crates/client181/src/minecraft_input.rs) has no leave-bed UI action. The missing presentation/input integration is separate from the working `World::tick_sleeping_players` time advancement. Left unchanged because it is neither a crash nor a hang.

### Q4 — Open harness limitation: scripted wheel does not scroll an open GUI

[menu-worlds/creative_inventory.png](../target/qa/menu-worlds/creative_inventory.png) and [creative_inventory_scrolled.png](../target/qa/menu-worlds/creative_inventory_scrolled.png) show the same catalog after a script `scroll`. Actual scrollbar drag reaches the bottom catalog in [creative/catalog_bottom.png](../target/qa/creative/catalog_bottom.png).

Cause: [crates/client181/src/app.rs](../crates/client181/src/app.rs), `App::script_step` / `Command::Scroll`, unconditionally queues the wheel in `minecraft_events.mouse`. Its native `WindowEvent::MouseWheel` handler instead calls `screen.mouse_scrolled` when a screen is open. [gui/screens/container.rs](../crates/client181/src/gui/screens/container.rs), `GuiContainer::mouse_scrolled`, contains the creative GUI scrolling path that the script bypasses. This evidence establishes a script routing gap, not a native wheel failure. Left unchanged under the fix restriction.

Worktree changes: the two menu-state conditions/comment in `crates/client181/src/app.rs`, and this report. All scripts, QA helpers, screenshots, logs, saves, and review/verification JSON files are under ignored `target/qa/`. `cargo build --release -p client` and `git diff --check` passed.
