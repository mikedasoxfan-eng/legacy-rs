# PlayerController / PlayerControllerSP b1.8.1 delta audit

Both original source classes were compared with their b173 counterparts. The complete differences are retained in target/player-gui7-base-controller.diff and target/player-gui7-survival-controller.diff. This audit credits the vanilla singleplayer class deltas, not Minecraft's entire application lifecycle.

| Changed or previously unproven part | Production port and original-bytecode evidence |
| --- | --- |
| Base becomes abstract; click/removing/reset/reach/HUD/place become abstract | The existing mode-aware controller delegates survival and creative behavior through the existing player APIs. controller181 and controllerinput181 exercise actual original controller methods and queued/held input. No removed base click or placement implementation is used as a fallback. |
| Base test-mode field rename and all six new presentation/reach flags | controllermode181 compares the original flags, reach, update policy and supplied-player initialization over 10,000 cases. |
| Base block-removal null guard | Creative removal uses the base return-false policy for air. Survival still performs canHarvestBlock(null) after the base false return. controllerlife181 proves the original NullPointerException and the port's caught panic; normal controller replays prove effects, metadata, removal and block hooks. |
| Base createPlayer and new SP createPlayer delegation | The shared factory calls the existing Entity::player and assigns the provider dimension. controllerlife181 compares 1,000 original factories with all three original provider IDs, varied spawn coordinates, four usernames, position/bounds, rotations, health, inventory and SP/container identity. |
| Survival flipPlayer / inherited creative no-op | The same 1,000 cases compare current and previous yaw/pitch after the actual original callback. Production spawn and respawn now call this policy; creative no longer receives the survival -180-degree yaw. The respawn edit is only a factory call and a flip callback at the existing owner integration points. |
| World callback, creative slot/drop callbacks, inherited initialization/update no-ops | Original callbacks are invoked by controllerlife181 and controllermode181. No independent world or inventory implementation was introduced. |
| New base stop-use callback | controllerlife181 calls actual func_35638_c for 256 supplied-player sword/food/bow/block/no-use cases and compares use stack, duration, blocking and equipped stack. Existing bow/input replays additionally prove release effects and queued stop policy. |
| SP explicit HUD and survival-interaction flag | controllermode181 compares actual original methods; survival returns true and creative uses its own inherited/overridden flags. |
| SP block permission checks | Original EntityPlayer.func_35190_e is unconditionally true for the vanilla player. Existing mining/click APIs retain that behavior; no alternate block permission system was added. controller181/controllerinput181 exercise the affected branches. |
| SP renamed block target fields and item-destruction callback | Existing target/reset/mining and destroy_held_block181 APIs retain all values and the no-op item-destruction callback. Controller/input, inventory and container replays cover durability, zero-sized equipped cleanup and harvest callbacks. |
| SP placement moves from the base; world/factory overrides delegate to base | Existing activation-first/null-stack/item-use policy is covered by controller181/controllerinput181. Factory delegation is independently checked by controllerlife181. |
| SP interpolation/reset/update lifecycle | controllerlife181 compares both original GUI/render damage outputs and retained private fields for 20,000 cases, including signed zero, subnormal, infinities, NaN, negative damage and out-of-range partial ticks. Reset preserves previous damage and the sound counter. controllermode181 independently proves survival update/music and creative no-op behavior. |
| Remaining unchanged base methods | Use, entity interaction/attack, window click and close delegate to the existing player/container APIs. Retained whole-player, combat, input, 66,146 container records and GUI-close checks remain the evidence for those unchanged paths. |

No world renderer, lightmap, entity model/renderer, block ticking, save format or terrain algorithm was changed.
